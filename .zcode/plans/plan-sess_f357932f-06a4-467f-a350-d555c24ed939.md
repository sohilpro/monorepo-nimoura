## Context

در audit read-only مشخص شد که بخش بنر از نظر قرارداد API و نمایش تا حد زیادی اصلاح شده، اما چند باگ runtime باقی مانده که می‌تواند باعث 500، orphan شدن فایل‌ها، حذف ناخواسته بنرها، یا نمایش نادرست وضعیت‌ها شود. مهم‌ترین مشکل این است که مدل دیتابیس بنر/جایگاه در source migration ندارد، درحالی‌که `synchronize` در production خاموش است.

## یافته‌های قطعی

### بحرانی
1. **نبود migration ساخت `banners` و `banner_positions`**
   - فقط entityها وجود دارند و migrationهای موجود صرفاً indexهایی روی `banners` می‌سازند.
   - `apps/api/src/common/database/database.module.ts` و `data-source.ts`، `synchronize: false` و `migrationsRun: true` دارند.
   - روی دیتابیس تازه یا محیطی که schema دستی ندارد، API در query/create با خطای relation does not exist شکست می‌خورد.
   - راهکار: migration کامل برای enumها، دو جدول، FK، soft-delete columns، indexها و seed idempotent جایگاه‌های استاندارد؛ lifecycle seed فعلی نیز باید فقط fallback باشد، نه جایگزین migration.

2. **ویرایش بنر با `positionId` نامعتبر ممکن است 500 بدهد**
   - `BannersService.update` در `apps/api/src/modules/banners/banners.service.ts` فقط banner را می‌خواند و `Object.assign` می‌کند؛ وجود position جدید را بررسی نمی‌کند.
   - راهکار: validate position در update و تبدیل نقض FK/DB به خطای 4xx واضح.

3. **آپلود تصویر در update به owner واقعی بنر منتقل نمی‌شود**
   - create بعد از save `reassignOwner` دارد، اما update ندارد.
   - وقتی در فرم ویرایش تصویر جدید آپلود می‌شود، رکورد media با owner موقت باقی می‌ماند و در cleanupهای بعدی ممکن است orphan یا حذف‌نشده بماند.
   - راهکار: update را transactional/جبرانی کنید، URLهای جدید را به owner بنر منتقل کنید، و فایل‌های قدیمی را فقط بعد از موفقیت ذخیره پاک کنید.

4. **حذف جایگاه می‌تواند بنرها را cascade کند ولی media را پاک نکند**
   - `BannerPosition` رابطه `onDelete: 'CASCADE'` دارد، اما `BannerPositionService.remove` فقط position را remove می‌کند.
   - نتیجه: با حذف یک جایگاه، بنرهای آن حذف می‌شوند ولی فایل‌ها و رکوردهای media می‌توانند orphan بمانند.
   - راهکار: قبل از حذف position، وجود banner را بررسی و حذف را منع کنید، یا حذف را به service بنرها بسپارید و media cleanup را کامل انجام دهید. گزینه امن پیشنهادی: تا وقتی بنر دارد، حذف position ممنوع و فقط deactivate مجاز باشد.

### مهم
5. **`maxItems` تعریف شده اما enforce نمی‌شود**
   - `BannerPosition.maxItems` در entity و UI وجود دارد، ولی `BannersService.create` و `findActiveForPosition` آن را لحاظ نمی‌کنند.
   - جایگاهی که maxItems=2 دارد می‌تواند تعداد نامحدود بنر active نمایش دهد.
   - راهکار: در create/update محدودیت active/scheduled را با query و transaction enforce کنید؛ در public query نیز دفاع دوم (`take(maxItems)`) اعمال شود.

6. **وضعیت‌های `scheduled` و `expired` کامل پیاده نشده‌اند**
   - public فقط `status=active` را برمی‌گرداند.
   - `expireOutdatedBanners` وجود دارد اما هیچ `@Cron` یا taskای آن را فراخوانی نمی‌کند.
   - scheduled هیچ transition خودکاری به active ندارد و expired نیز فقط در صورت فراخوانی دستی تغییر می‌کند.
   - راهکار: task دوره‌ای برای فعال‌سازی scheduled در startAt و expire کردن active در endAt؛ همچنین public query با بازه زمانی دفاع کند.

7. **خطای 500 بعد از upload هنوز می‌تواند فایل موقت بسازد**
   - upload قبل از create انجام می‌شود و owner پیش‌فرض `temp` است.
   - اگر create به‌هر دلیل fail شود، فایل و media موقت باقی می‌ماند.
   - راهکار: cleanup جبرانی در admin/backend یا job cleanup برای mediaهای temp قدیمی؛ ترجیحاً create flow با شناسه draft/transaction طراحی شود.

8. **auto-seed در `onModuleInit` خطا را swallow می‌کند**
   - `BannerPositionService.onModuleInit` هر خطا را فقط log می‌کند.
   - اگر جدول وجود نداشته باشد، API بالا می‌آید ولی پنل جایگاه خالی و ساخت بنر fail می‌شود.
   - راهکار: migration را مرجع اصلی کنید و خطاهای schema را در startup fatal کنید؛ swallow فقط برای خطای duplicate/همزمانی مجاز باشد.

### متوسط
9. **محدودیت key در PositionManager فقط HTML است**
   - backend `CreatePositionDto` صرفاً string/maxLength دارد؛ keyهای دارای فاصله/حروف بزرگ/اسلش در API قابل ایجادند و URL public را شکننده می‌کنند.
   - راهکار: `Matches(/^[a-z0-9]+(?:-[a-z0-9]+)*$/)` در DTO و normalize/duplicate check case-safe.

10. **`UpdatePositionDto` امکان تغییر key را باز می‌گذارد بدون کنترل duplicate**
   - `BannerPositionService.update` فقط `Object.assign` و save دارد؛ conflict key می‌تواند به DB error/500 تبدیل شود.
   - راهکار: قبل از update duplicate key را با exclude id بررسی و ConflictException بدهید.

11. **public tracking برای id غیرموجود silently success می‌شود**
   - `incrementView/click` فقط `repository.increment` می‌زنند و affected را چک نمی‌کنند.
   - راهکار: affected=0 را 404 یا no-op کنترل‌شده کنید؛ حداقل ParseIntPipe فعلی حفظ شود.

12. **حذف position فعلی API با بنرهای وابسته ممکن است پاسخ generic DB error بدهد**
   - علاوه بر orphan media، کاربر پیام فارسی مشخص دریافت نمی‌کند.
   - راهکار: ConflictException با تعداد بنرهای وابسته.

13. **فرانت فقط پاسخ API را normalize می‌کند، اما error state را نمایش نمی‌دهد**
   - `useBanners` در failure فقط لیست خالی و loading state می‌دهد؛ تشخیص backend outage از no-banner دشوار است.
   - راهکار: error را return کند و Slot در صورت خطای واقعی logging/observability کنترل‌شده داشته باشد؛ UI لازم نیست error خام نشان دهد.

14. **کش public بعد از create/update/delete تا ۱۵ ثانیه stale می‌ماند**
   - `CacheInterceptor` روی public endpoint فعال است و invalidation بعد از mutation وجود ندارد.
   - راهکار: cache key/version یا invalidate مشخص برای position بعد از mutation؛ در حداقل حالت TTL کوتاه‌تر و مستندسازی رفتار.

## Implementation plan بعد از تأیید

1. ایجاد migration کامل banner schema و seed استاندارد با همان `BANNER_POSITIONS`؛ جلوگیری از وابستگی production به `synchronize`.
2. ساخت helper مشترک در `BannersService` برای validate position، validate dates، maxItems و media URLs.
3. اصلاح create/update در transaction یا الگوی جبرانی: انتقال media جدید، cleanup در failure، جلوگیری از orphan شدن فایل‌ها.
4. اصلاح position service: key validation، duplicate-safe update، جلوگیری امن از delete جایگاه دارای بنر و پیام ConflictException.
5. اضافه‌کردن scheduler برای scheduled/expired و تست public filtering/maxItems.
6. اصلاح tracking affected count، cache invalidation و error propagation کنترل‌شده.
7. اصلاح فرانت/admin برای نمایش خطا، حذف fallbackهای ناامن، جلوگیری از ارسال URL/object نامعتبر و هماهنگی کامل response envelope.
8. افزودن تست‌های unit/integration برای create/update/delete position، maxItems، lifecycle وضعیت، media reassignment، public response و cache behavior.

- تست خطاهای position نامعتبر، key تکراری، maxItems، scheduled و expired.

در این مرحله هیچ فایلی تغییر داده نشده است؛ این گزارش نتیجه audit read-only و برنامه اصلاح پیشنهادی است.
